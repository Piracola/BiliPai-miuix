## 初学者解释

UI 设计并不只是“画得好看”。在 Android 项目里，它还要告诉代码：同一种按钮在哪里都应代表同一种操作，加载失败时用户能做什么，屏幕变宽后内容如何重排，以及读屏软件能否理解页面。

| 术语 | What：是什么 | Why：为什么重要 | How：在本项目怎样使用 |
|---|---|---|---|
| Jetpack Compose | 用 Kotlin 函数描述界面的 Android UI 工具 | 状态变化后界面可以自动重新计算 | 页面用 `@Composable` 函数组合，叶子组件接收状态和回调 |
| Composable | 带 `@Composable` 的界面函数 | 是 Compose 的基本搭建单位 | 例如 `AppButton`、`AppCard`、`AppScaffold` |
| Design Token | 给设计数值起的语义名称 | 修改主题或风格时不用全项目逐个改数字 | 间距用 `AppSpacingTokens`，圆角用 `AppShapes` |
| 语义组件 | 按“用途”命名的可复用组件 | 避免同一种用途出现多套行为 | 通用按钮走 `AppButton`，播放器操作可保留领域组件 |
| 原语组件 | 文本、图标、表面、按钮等最小构件 | 为双主题提供统一入口 | `AppText`、`AppIcon`、`AppSurface` 等 |
| 页面母版 | 一类页面共用的结构规则 | 列表页不必各自重新发明加载与错误布局 | 页面先选择母版，再补业务差异 |
| NavKey | Navigation 3 中代表一个目的地的数据类型 | 它是页面覆盖范围最可靠的清单 | 每个 `BiliPaiNavKey` 必须在页面目录出现一次 |
| 路由 | 从一个页面到另一个页面的地址或规则 | 决定入口、参数和返回关系 | 以 `routeBase` 记录稳定路由名 |
| 状态 | 页面在某个时刻的数据与交互情况 | 用户不只会看到“正常数据” | 至少考虑加载、空、失败、离线、未登录和分页 |
| 状态提升 | 把状态放在更上层，子组件只接收值与事件 | 更容易测试，也避免同一状态多处不同步 | Screen 管理状态，叶子组件接收不可变值和 lambda |
| 响应式布局 | 根据可用空间重新组织内容 | 平板不是把手机页面简单拉宽 | Compact 单栏，Medium/Expanded 可双栏或侧栏 |
| 断点 | 布局发生结构变化的宽度门槛 | 让变化发生在可解释的位置 | 共享基线外，840/960/1600dp 等特例必须说明场景 |
| dp | Android 的布局尺寸单位 | 在不同像素密度设备上保持接近的物理大小 | 触摸目标至少 48dp，间距从共享 Token 取值 |
| sp | Android 的文字尺寸单位 | 会响应用户的系统字体大小 | 正文和标题使用主题 typography，不用 dp 写字号 |
| 可访问性 | 让视觉、听觉或动作能力不同的人也能操作 | 是功能正确性的一部分，不是装饰 | 提供名称、角色、状态、顺序和足够触摸区域 |
| Content Description | 给非文字图标或图片的可访问名称 | 读屏不能从图形猜出含义 | 可点击图标必须有说明；纯装饰图标设为 `null` |
| 对比度 | 前景与背景亮度差 | 过低会使文字或状态不可辨认 | 使用主题角色色，并在明暗主题下检查 |
| 深色模式 | 系统或应用使用暗色表面的主题 | 不是简单把所有颜色反转 | 由主题角色映射，媒体和品牌色单独检查 |
| AMOLED 模式 | 尽量使用纯黑背景的暗色变体 | 可满足特定屏幕和用户偏好 | 只改变背景策略，不改变信息和交互 |
| Miuix | Miuix Compose 组件与视觉能力 | 是本项目的默认主设计方向 | 以 0.9.3 当前能力作为主要映射和完整验收基准 |
| iOS 历史值 | 旧版设置中可能保存的 iOS 预设 | 保障旧数据可迁移 | 仅在迁移时归入 MIUIX，不进入运行时主题或验收矩阵 |
| Material 3 | Android 官方 Material 设计组件体系 | 是 Android 原生兼容路径 | 作为关键流程兼容验收对象 |
| Scaffold | 组织顶部栏、内容、底栏等页面外壳 | 防止内容被系统栏或导航栏遮挡 | 使用 `AppScaffold`，不要在业务页重复造壳 |
| Surface | 承载背景、形状、边框和点击的表面 | 颜色与层级应由语义决定 | 使用 `AppSurface` / `AppSurfaceTokens` |
| Overlay | 覆盖在当前内容上的弹层或控制层 | 会影响焦点、返回和手势 | 对话框、底部面板、播放器控制层均需明确关闭规则 |
| 性能预算 | 页面允许消耗的绘制、内存和重组成本 | 卡顿也是 UI 缺陷 | 列表稳定 key，避免组合期重活，效果支持降级 |
| 降级 | 设备能力不足时换用较轻效果 | 保证功能优先于视觉特效 | 模糊失败时用不透明表面，减弱动画时保持状态变化可见 |

## 规范要求

- **必须**在专业词第一次出现时给出中文解释或链接本页。
- **必须**把功能语义与视觉外观分开，例如“主操作”是语义，“粉色圆角按钮”只是某风格的表现。
- **应该**优先使用本项目符号名说明代码入口，并补充通俗中文用途。
- **禁止**用“感觉差不多”“参考某 App”代替可验收规则。

## Compose 短示例

```kotlin
AppIconButton(
    onClick = onBack,
    icon = rememberAppBackIcon(),
    contentDescription = "返回"
)
```

这里 `AppIconButton` 是原语入口，“返回”是可访问名称，`onBack` 是由上层传入的事件。

## 代码映射

- 组件原语：`AppPrimitiveComponents.kt`
- 页面外壳：`AdaptiveChrome.kt` 中的 `AppScaffold`、`AppTopBar`
- 导航页面：`BiliPaiNavKey.kt`
- 主题预设：`UiPreset.kt` 及应用侧 `UiStyle`

## 当前差距

旧页面注释和组件命名仍混用“样式”“组件”“功能”等词；部分可点击图标使用 `contentDescription = null`。后续整改必须按语义逐项判断，不能机械替换所有 `null`。

## 验收方法

让一名不了解代码的人阅读任一组件档案：他应能说出组件解决什么问题、何时不能用、正常和异常状态有什么区别，以及应该从哪个 Compose 入口开始。
