# 动画与转场性能优化计划

日期：2026-07-30  
目标设备：Redmi K60，骁龙 8+ Gen 1  
状态：待实施  
依据：`ANIMATION_PERFORMANCE_AUDIT_2026-07-30` 的静态审查结论

## 1. 目标

本计划的重点不是简单缩短动画或关闭全部模糊，而是避免在同一帧内同时执行重组、布局、全屏背景采样、视频纹理合成、Surface 切换和显示模式切换。

优化完成后应达到：

- 60Hz 下，转场 p95 帧耗时低于 16.67ms，单次转场不出现超过 100ms 的主线程停顿。
- 120Hz 下，大多数动画帧接近或低于 8.33ms，避免连续多帧超时。
- 冷机与连续往返 30 次后的 p95 差异不超过 15%。
- 默认性能档不出现黑帧、白屏、封面跳变、视频瞬断或底栏闪烁。
- 10 分钟播放后重复转场时，不因动画造成明显热降频。

性能数值必须在 Redmi K60 真机上确认。源码分析只能证明高风险路径存在，不能替代真机的 CPU、GPU 和 thermal 数据。

## 2. 当前基础与改造原则

项目已经具备以下可复用基础：

- `MotionTier`：控制动效和模糊等级。
- `RuntimeVisualGuardTracker`：根据连续掉帧进行事后降级。
- 返回封面接管路径：可隐藏实时播放器并保留播放器会话。
- `VideoOutputRouter`：集中管理直出 Surface 和 Anime4K 输出绑定。
- Macrobenchmark：已覆盖视频卡进入、返回、预测返回和部分滚动场景。

这些机制不能直接当作完整答案：`MotionTier` 目前不控制刷新率、播放器输出、弹幕或 Anime4K；运行时守卫也要累计掉帧后才触发。因此本计划采用“转场性能快照”作为统一入口，而不替换已有 `MotionTier`。

每次改动遵循以下原则：

1. 一次只处理一个可测量的性能原因，并单独提交。
2. 先保留播放器会话、进度和缓冲状态，再决定是否暂停视频输出；不能为了省资源引入黑帧或白屏。
3. 转场期间冻结配置变化，转场结束后再统一应用。
4. 不把“关闭所有模糊”或“延迟创建播放器”当作通用方案。
5. 不读取或分析截图。视觉正确性由真机人工检查，性能数据由脚本、Macrobenchmark、Perfetto 和 dumpsys 采集。

## 3. 总体顺序

| 批次 | 内容 | 主要收益 | 依赖 |
| --- | --- | --- | --- |
| M0 | 建立真机基线和采集口径 | 后续有可靠对照数据 | 无 |
| M1 | 转场性能快照和统一预算 | 为各组件提供同一决策来源 | M0 |
| M2 | 预测返回、刷新率、播放器输出峰值削减 | 解决最主要的转场掉帧和发热来源 | M1 |
| M3 | 弹幕、Anime4K、首页背景和离屏任务 | 降低持续 GPU/CPU 负载 | M2 |
| M4 | 重布局和局部高成本动画 | 降低滚动、抽屉和列表切换负担 | M3 |
| M5 | Baseline Profile 与长期性能护栏 | 防止后续版本回退 | M2-M4 稳定后 |

## 4. M0：先记录基线

### 任务

1. 使用现有 `BiliPaiVideoDetailFrameTimingBenchmark` 记录视频卡进入、顶部返回、系统返回、预测返回提交和取消。
2. 补充“同一张卡片进入 -> 等首帧 -> 返回”连续 30 次的热机场景。
3. 扩展 `scripts/card_transition_gfxinfo.sh` 和 `scripts/mobile_perf_collect.sh` 的采集项：
   - p50、p95、p99、janky frames、连续超时帧。
   - thermal status、CPU/GPU 频率、实际刷新率、功耗或电池电流/电压。
   - 冷机首轮、播放 10 分钟后、连续往返后的时间线。
4. 为转场添加稳定 trace section，至少区分 Compose 布局、背景模糊、Surface 输出变化、图片解码和播放器 Overlay。

### 验收

- 每组数据记录设备温度状态、刷新率、卡片转场开关、模糊设置、弹幕状态、Anime4K 档位和测试视频。
- 采集窗口与操作步骤固定，能够重复运行。
- `gfxinfo` 仅用于低侵入帧统计；定位 CPU/GPU 原因时另行使用短时间 Perfetto 或系统计数器。

## 5. M1：转场性能快照

### 设计

新增 `TransitionPerformanceSnapshot`，在转场开始前确定并锁定到转场结束。它不是替换 `MotionTier`，而是把既有动效档位和播放器策略组合成一次转场的统一决定。

建议的档位：

| 档位 | 使用条件 | 转场策略 |
| --- | --- | --- |
| FULL | 冷机、非省电、温度正常、近期帧耗时健康 | 可允许有限实时视频形变和动态模糊 |
| BALANCED | 默认 | 封面 morph、SurfaceView、冻结或降低模糊、暂停非必要 Overlay |
| CRITICAL | 省电、温度高、系统减弱动效或近期连续掉帧 | 仅位移和透明度、无动态模糊、60Hz、封面接管 |

快照至少包含以下字段：

- 当前档位和派生出的 `MotionTier`。
- 是否允许实时视频参与共享变形。
- 是否暂停弹幕、字幕、互动卡和播放器控制层。
- 是否允许 Anime4K。
- 是否允许刷新率、Surface 或输出路由在转场中变更。
- 当前视觉预算：动态模糊、低分辨率快照或半透明纯色。

### 输入与接入点

- 系统减弱动效。
- `PowerManager` 的省电状态。
- Android thermal status；低版本或无法读取时采用保守默认值。
- 现有 `RuntimeVisualGuardTracker` 的降级决定。
- 当前转场类型：视频卡共享转场、普通预测返回、抽屉或页面模式切换。

不要把播放器专用字段放进 `MotionTier`。`MotionTier` 保持现有含义；快照的纯策略部分可做成可单测的 Policy，视频模块再把快照映射为 Surface、Overlay 和 Anime4K 行为。

### 验收

- 同一场转场中档位不变化。
- 转场取消、完成、Activity 重建后均能正确释放快照。
- 增加 Policy 单元测试，覆盖 FULL/BALANCED/CRITICAL、省电、热状态、减弱动效和掉帧守卫组合。

## 6. M2：优先削减转场峰值

### M2-1：刷新率策略

当前视频详情会直接请求不低于 90Hz 的最高显示模式。改为：

1. 进入和返回转场期间保持进入前的刷新率，不修改 `preferredDisplayModeId`。
2. 页面稳定后，再根据视频帧率和性能快照选择显示模式。
3. BALANCED/CRITICAL、省电或温度升高时优先 60Hz。
4. 不在返回动画起点切换刷新率。

先完成“转场中不切换”的低风险改动，再根据 K60 实测决定稳定播放期的 60/90/120Hz 选择细节。

### M2-2：默认封面 morph 与 SurfaceView

当前共享转场开关会让播放器长期使用 TextureView。改为：

1. 默认播放保持 SurfaceView。
2. 共享转场使用视频卡封面或已有驻留封面参与 morph。
3. 只有水平/垂直翻转等确实需要纹理变换的功能，或 FULL 档明确允许时，才临时使用 TextureView。
4. `navigationTransformEnabled` 不再单独决定整个播放生命周期的输出类型。

已有“强制封面接管”路径可先用于 BALANCED/CRITICAL。第一步只隐藏实时画面并关闭 Overlay，保留 Surface 绑定；确认无黑帧后，再在性能档下评估暂停解码或解绑输出。

### M2-3：冻结输出路由与 Anime4K

转场中禁止执行以下变化：

- Surface 解绑或重绑。
- Anime4K 开关、FAST/QUALITY 切换、输入尺寸调整。
- 显示刷新率切换。

`VideoOutputRouter` 收到的变化暂存，转场完成后在下一帧或空闲阶段统一应用。任意转场期间 Anime4K 强制 bypass；质量档不能与实时共享返回同时执行。

### M2-4：普通预测返回并行收尾

当前普通预测返回在提交后先等待模糊清理，再执行 550ms 全页滑出。改为：

1. 手势提交后立即执行页面返回。
2. 模糊清理、当前页退出和目标页稳定化并行。
3. 总收尾调整为 220-280ms，保留现有目标页全屏逻辑。
4. 模糊半径只使用少量量化档位，并缓存 `RenderEffect`，避免逐帧新建对象。

视频卡共享返回已经排除普通预测返回模糊，两个路径保持独立，不能误改为双层模糊。

### M2 验收

- 60Hz 下单次转场无超过 100ms 的主线程停顿。
- BALANCED 默认档下返回不出现黑帧、白屏、封面跳变、音频泄漏或底栏闪烁。
- `VideoDetailReturnCoverPolicyTest`、`VideoPlayerSectionPolicyTest`、`Anime4KOutputPolicyTest`、预测返回策略测试全部通过。

## 7. M3：降低持续负载

### 视频播放路径

1. 转场期间统一隐藏或冻结高级弹幕、标准弹幕、命令弹幕、字幕、互动卡和控制层。
2. 高级弹幕取消固定 16ms 的 Compose 全表扫描；优先建立开始/结束时间索引，后续再评估 Canvas 单次绘制。
3. Anime4K 增加 thermal、省电、刷新率和帧耗时旁路；恢复时只在转场结束后应用。

### 首页路径

1. 建立单一“当前帧背景源”所有权，避免 Kyant、Miuix、Haze 同时录制全屏内容。
2. Pager 的连续 offset 下沉到 `graphicsLayer` 或 draw 阶段读取，避免 Composable 主体逐帧重组。
3. LazyGrid 只使用稳定业务 ID 作为 key；统一预取和展示的 URL、尺寸与 cache key。
4. 为保留的顶级页面下发 `isTopLevelActive`，离屏页面停止无限动画、自动播放、传感器和高频轮询。

### 音频、番剧和直播路径

1. 音频页背景采用封面变化时生成的低分辨率预模糊缓存；播放进度拆成独立小状态。
2. 番剧播放器统一进度轮询，只在页面可见、播放器播放、控制层需要时运行；SponsorBlock 同样随生命周期暂停。
3. 直播聊天使用稳定 receipt id、环形缓冲或反向列表；自动跟随改为节流后的 `scrollToItem`，仅在用户恢复跟随时动画滚动一次。

## 8. M4：减少逐帧布局

以下场景不再逐帧改变真实宽高、padding 或保留两套重页面树：

- 动态页模式切换、番剧筛选、评论楼中楼。
- 横屏播放器末端抽屉和平板影院侧栏。
- 动态页/番剧页滚动阈值处的高度动画。
- 删除卡片的粒子、抖动和列表收拢。

优先使用固定尺寸 Overlay、`graphicsLayer.translationX`、裁剪和透明度。动画结束后再一次性提交最终布局约束。粒子删除效果在 BALANCED/CRITICAL 仅保留约 135ms 的 alpha/scale，不能同时启动 PixelCopy、连续 GL、全屏抖动和逐帧高度动画。

## 9. M5：长期性能护栏

1. 在得到稳定结果后接入 `androidx.baselineprofile` 插件并生成发布包可用的 Baseline Profile。当前只有 ProfileInstaller 依赖，尚未把 profile 产物接入 app。
2. 将“卡片进入 -> 首帧 -> 返回”热路径、预测返回、SurfaceView/TextureView、番剧播放器加入 Baseline Profile 和 Macrobenchmark。
3. Macrobenchmark 除 `FrameTimingMetric` 外增加可归因的 trace 指标；长期热衰减继续通过真机 Perfetto 和系统计数器采集。
4. 扩展 `FrameBudgetLintTest`：不仅限制 `createBlurEffect` 数量，也检查高风险调用点不会在动画帧内重复创建效果对象。

接入 Gradle 插件或新增依赖前，需要单独确认版本兼容性和构建影响。

## 10. 每批交付流程

每个 M 阶段内的子任务独立提交并推送，流程固定为：

1. 先补纯 Kotlin Policy 测试或现有策略测试。
2. 完成小范围实现。
3. 运行对应单元测试和 `:app:compileDebugKotlin`。
4. 在 K60 上执行相同基线动作，比较改动前后数据。
5. 人工确认返回落位、封面、视频、底栏和手势取消逻辑；不使用截图分析。
6. 只有达到该批验收标准才进入下一批，否则回退该批或调整策略。

## 11. 真机检查清单

每次性能改动至少验证：

- 60Hz / 120Hz。
- 卡片共享转场开 / 关。
- 顶栏、底栏实时模糊或液态玻璃开 / 关。
- 弹幕关 / 普通弹幕 / 高级弹幕较多的视频。
- Anime4K 关 / FAST / QUALITY。
- 冷机首轮、连续往返 20-30 次、播放 10 分钟后。
- 预测返回慢拖取消、慢拖提交、快速提交。

需要记录 p50/p95/p99、janky frames、连续超时帧、主线程 Compose 时间、RenderThread/GPU/SurfaceFlinger 时间、thermal status、CPU/GPU 频率和首次降频时间。

## 12. 首批不处理的内容

冷启动飞出动画、首次引导 Lottie、清缓存弹窗、默认关闭的底栏搜索布局、平板专用影院侧栏等 P2 项目不进入 M2。它们在 M4 之后按真实设备数据排序，避免分散首批对视频卡转场的处理能力。
